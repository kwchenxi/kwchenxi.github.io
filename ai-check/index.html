用 AI 做 UI 走查

Hoho · 2026-08-04 · 阅读约 5 分钟
01 / 起因

为什么让 AI 做走查

传统设计走查又慢又主观，而且很多产品是桌面客户端—它们不像网页那样容易自动化测试，常见的网页测试工具根本用不上。只有让 AI 真正“坐到电脑前”像人一样操作，才有解。

于是我们做了一个实验：让 AI 像测试工程师一样，打开真实应用、拖拽窗口、点击按钮、截取各种状态，自己判断页面有没有问题。后来又逐步加上了代码扫描、Figma 设计稿对比等能力，形成一套完整的走查方案。

AI 特别擅长几类活儿：系统地测试各种窗口尺寸、对照规范检查实现偏差、批量扫描代码里的硬编码。而像颜色是否和谐、留白是否舒适这种需要设计直觉的判断，仍然是人的主场。

03 / 技术手段

四个能力支柱

不是让 AI “看一眼截图打分”，而是让它像真人测试员一样操作应用、扫描代码、对比设计稿。背后依赖四个关键技术：

🖥️

界面操作

AI 直接操控桌面：拖拽窗口测试响应式、点击按钮、在输入框打字、截图取证。相当于一个能看屏幕的远程测试员。

🔍

代码扫描

解包应用代码，用正则匹配检查：颜色、圆角、字号是否使用了设计系统的变量，而不是写死具体数值。

🎨

Figma 对比

通过 Figma API 拉取设计稿截图，与实际页面逐项对比，发现设计稿到实现的偏差。

📋

规范对照

访问设计规范站，提取按钮高度、间距网格、字号等具体数值，作为走查的评判基准。

04 / 走查流程

从打开应用到输出报告

整个过程不需要写测试脚本。如果有 Figma 设计稿，还可以自动对比设计和实现的差异。AI 就像一个刚入职的测试同学，但速度比人快 3-5 倍，而且不会遗漏检查项。

打开应用 & 截取基准

AI 操控桌面打开灵基应用，截取默认窗口状态作为基准截图。

窗口缩放极限测试

拖拽窗口到最小尺寸（测试响应式）、窄宽度、全屏最大化，每个状态截图记录布局问题。

交互操作测试

点击筛选器、下拉框、搜索、按钮，快速连续操作，测试加载态、面板残留、焦点状态等交互细节。

规范对照

访问设计规范站，提取按钮尺寸、间距规则等数值，作为判断基准。

输出 HTML 报告

将所有发现按严重/中等/轻微分级，嵌入截图，生成可交互的 HTML 走查报告。

05 / 思考

AI 走查的边界在哪里

实验下来，有几个比较明确的结论：

✓

响应式 & 布局问题发现率很高。AI 可以系统地测试多种窗口尺寸，不遗漏截断、溢出、列数不降等问题。这类问题人工走查经常漏。

✓

规范偏差检查很稳定。只要规范数值明确（如按钮高度 28px），AI 就能准确判断实际实现是否偏离，不受主观影响。

▵

视觉美感判断还做不了。颜色搭配是否和谐、留白是否舒适、视觉层次是否清晰 — 这些需要设计直觉的问题，AI 目前只能给出“符合/不符合规范”的二元判断。

▵

交互逻辑深度不足。对于需要多步骤、多状态联动的复杂业务逻辑（如审批流程），AI 只能测试表层 UI，无法理解业务流程是否正确。

✓

代码扫描能发现人眼看不到的问题。通过解包代码，可以批量找出所有没用设计变量的地方，按模块拆分，精准定位哪些业务需要改进。这类问题人工走查根本发现不了。

✓

Figma 对比让设计还原可量化。直接拿设计稿和实现截图对比，自动发现名称格式、状态缺失、布局差异等问题，比人工逐像素对比高效得多。

✓

回归验证很高效。代码修复后重新跑一遍，自动生成 v0.1.2→v0.1.3 的对比报告，哪些改了哪些没改一目了然。

✓

未来方向：AI 走查 + 人工审核。AI 负责批量扫描布局、代码规范性问题和设计还原度，人工聚焦在设计意图和业务逻辑的验证上，效率可以提升 3-5 倍。
