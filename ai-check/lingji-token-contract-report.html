金蝶灵基 — Token 合同审计报告

审计框架：Lingee §3.8 Token 合同 代码基线：v0.1.3（Electron / app.asar） 扫描时间：2026-08-11 状态：registered · audit pending

这是什么？

《Lingee 通用页面生成与验收规范》§3.8 定义了一套 Token 合同：七份 JSON 文件是设计系统的机器可读事实源，配套有颜色依赖方向、alias 规则、消费边界、审计与发布条件。这份报告把 上一份 Token 扫描 的原始数据，重新按合同框架对照检查，看灵基 v0.1.3 的代码实际用法与合同要求之间的距离。

合同当前整体状态为 registered_alias_audit_pending：七文件身份已登记，但未完成 alias 全图、跨层消费、直接值与命名迁移审计，也未固定 SHA-256。

1. Token 合同的七份文件

按 §3.8.1，下列七份工作区 JSON 是当前 Token 合同的机器可读事实源。文件名和 mode 大小写是身份的一部分，禁止规范化或按"看起来相同"替换。

2. 颜色依赖方向与消费边界

唯一允许的方向（§3.8.2）：
全局色板（primitive） → 语义色板 → 组件色板 → 组件实现
全局色板（primitive） → 语义色板 → 非组件实现

硬规则：组件实现只能消费自身命名空间的 Token；非组件页面只能消费语义 Token；全局色板永远不作为 DOM/CSS/SVG 实现入口。

典型违规点（按合同归类）

  • 登录页（login.css）：按钮、链接直接写 #495DFF——属于"非组件页面元素直接消费全局色板"，违反 §3.8.2 硬规则 3。
  • 小程序窗口 / WebView（miniapp.css、imageViewer.css）：大量使用 iOS 蓝 #007AFF 而非灵基主色——属于"使用合同外色值"，违反 §3.8.2 硬规则 1。
  • Toast / Checkbox / Spinner（JS 内联）：在 JS 字符串中硬编码色值——属于"经非声明路径消费"，违反 §3.8.2 硬规则 4。
  • Tailwind .text-[#495DFF]：绕开 Token 系统直接写色值——合同不承认这种表达，必须迁移到对应 semantic/component Token。

3. 主题色身份对照

身份说明：灵基 v0.1.3 实际代码使用 #495DFF 作为主色（对应代码中 --lg-primary-600）。新规范 §3.8.4 登记的 primary.500 = #6D80FF，可能与 primary-600 是同一色阶的不同档位，也可能代表产品后续的品牌色调整。在 Design System owner 裁决前，本报告按"代码事实 + 合同登记"两条线并列呈现，不擅自合并或替换。

5. Spacing 合同审计（§3.8.8）

合同登记 13 个 number Token，全部 scope=GAP。Figma 规范 12 条 hook，与本地 12 条能按 px 值匹配；0-5x-large = 24 是 Figma 覆盖缺口。

硬规则（§3.8.8.3 第 6–7 条）：spacing Token 只允许在"页面/组件 source-map 证明目标属性为 gap 且身份绑定成立"时消费。禁止自动用于 padding、margin、页面 gutter、定位偏移、width/height。

当前代码风险

上一份扫描未单独统计 spacing Token 使用情况。按合同要求，以下场景需要补扫并进入 token-audit.json：

  • 所有 padding: 16px / margin: 24px / gap: 12px 的硬编码——即使值匹配 Token，scope 只授权 gap，padding/margin 属于合同外使用。
  • 所有 width / height 用 spacing number 的地方——合同明确禁止。
  • 命名冲突：spacing-1.5x-small ↔ 1-5x-small、spacing-0.5x-small ↔ 0-5x-small、--sl-spacing-medium ↔ medium。禁止自动 normalize，需 Design System owner 裁决。

合同特殊项

  • radius-circle vs radius-pill：合同明确 circle = 50%H（仅当 width=height 时产生正圆）、pill = 999px（长条形）。本地 JSON 两者都解析为 999，但 Variable ID 不同，不能互换。当前 radius-circle 合同状态 block，所有代码里的"正圆"实现（如头像、图标容器）需验证是否满足 width = height 形状不变量。
  • 4 项 metadata defect：small / medium / large / x-large 的 $description="边框宽度" 与文件类型、scope、Figma 圆角表冲突——必须版本化描述修复，不得复制到生成文档。
  • scope 例外：4x-large scope=ALL_SCOPES，比其他 Token 更宽；消费审计仍只能允许其用于 radius 属性，不能因 scope 宽泛绕过语义。
  • 0 圆角缺口：两份来源都没有 0 圆角 Token，确认不能用最小 4 替代 0，也不能伪造 radius-none。代码里的 border-radius: 0 保持"合同外使用"，不进 Token 审计。

8. 升级到 bound 的必要条件

按 §3.8.10 与 §3.8.7/8/9 升级条件，当前 pending 状态升到 bound 需要：

  1. 固定七份 JSON 的真实 immutable version（不是 URL 参数 t=...）。
  2. 保存 Figma live read 的 raw response 与 SHA-256 hash。
  3. 取得每条 Token 的稳定 Variable ID 与 alias chain，关闭 cycle / unresolved / 跨层反向引用。
  4. 关闭命名冲突（spacing 3 个、radius description 4 个、typography 2 个）。
  5. 关闭 radius-circle blocker：选择裁决方案并版本化。
  6. 对主色身份（primary.500 #6D80FF vs --lg-primary-600 #495DFF）给出 Design System owner 裁决。
  7. 把所有硬编码与合同外使用登记进 token-audit.json，含 owner、原因、影响、审批、关闭策略。
  8. mapping unresolved/conflict = 0。
